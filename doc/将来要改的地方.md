  - 现象（探针实证，\\?\ 前缀枚举为硬证据；描述基于守卫插入前的原文件状态）：
    - ProjectName='Manga   ' 时，构建项目目录处的 New-Item -Path "$projectDir"（尾空格落在路径末段）
      产出裁剪空壳 2026-10-06_Manga；六次多级 New-Item（尾空格落在中间段）
      产出真身 2026-10-06_Manga 加三个尾空格。两者同时存在于磁盘，是两个独立条目
    - 真身内含完整子树（02_Preprocessing 下 4 个、03_Typesetting 下 2 个）；
      New-ReadmeFile 的 Join-Path 使尾空格落到中间段，Out-File -LiteralPath 跟随，
      因此 README.md 也写进真身
    - 用户在资源管理器中看到并操作的是空壳，整轮 workflow 一致跑完、不报错，用户无任何信号
  - 机制（已查明：不一致的唯一来源是尾空格落在路径末段还是中间段，
    与相对/绝对路径、-Force、Join-Path 均无关）：
    - New-Item -Path "$Base\x_   "（末段）→ 只有 x_（name.Length=2），尾空格被 Win32 规范化裁掉
    - [IO.Directory]::CreateDirectory("$Base\x_   \y")（中间段）→ x_ 加三个空格（name.Length=5）+ y，尾空格保留
    - New-Item -Path "$Base\x_   \z"（中间段）→ 同时出现 x_ 与 x_ 加三个空格：
      PowerShell 建多级目录时先用原始路径预建父目录，此时父路径尾空格落在末段被裁掉
    - New-Item 没有 -LiteralPath（实测抛 ParameterBindingException），无法用参数规避
    - 补充实测：制表符 / CR / LF 落在末段时 NTFS 直接抛 IOException（不只是静默裁剪）；
      NBSP(U+00A0) 与全角空格(U+3000) 保留、可寻址、不产生分裂；
      单点与 '..' 落在末段同样被裁剪，产出空壳与真身两个目录；前导空格保留且无害
  - 后果（真身目录用普通 provider 路径完全不可寻址）：
    - 仅存在尾空格目录时，Test-Path -LiteralPath 带尾空格 = False、不带尾空格 = False，仅 \\?\ 为 True
    - 两目录并存时尾空格被静默忽略，Get-Item 指向空壳、
      Remove-Item -LiteralPath <带尾空格> 会静默删掉空壳，真实数据变成 provider 删不掉的孤儿
    - 存量普查（只读，普通与 \\?\ 枚举计数一致）：01_Projects_Active 6 项、
      02_Archive_Completed 9 项、04_Temp/*_need_upscale 0 项，顶层全部 NO_SUSPICIOUS_ENTRIES
      —— 存量 0、无迁移负担，level-1 即本缺陷完整风险面，无需递归
  - 判据（本轮 Q2=c 精确字符集，按探针实证而非直觉设定）：
    - 拒绝三类：纯空白串；以 ASCII 空白（0x20/0x09/0x0A/0x0B/0x0C/0x0D）开头或结尾；以 '.' 结尾
    - 放行两类：NBSP(U+00A0)、全角空格(U+3000) 结尾 —— 实测既不被裁剪也可正常寻址，
      不为无害入参报错；放行用例必须存在，用以钉住「不误伤」承诺
    - 否定的两个候选判据：`$x -ne $x.Trim()`（按全 Unicode 空白判定，既过宽又漏尾点）

    - 尾点单列一条的依据：Win32 对末段尾部点的裁剪与尾空格同源，

## 重要但不紧急
[ ] 规则层通则：字符串参数应校验纯空白与首尾空白（重要但不紧急）
  - 目标文件：doc/project-rules/powershell-7-standard-project-rules.md
  - 通则要点：
    - [Parameter(Mandatory = $true)] 与 [ValidateNotNullOrEmpty()] 均放行纯空白串（实测），
      不能当作参数校验手段
    - 仅当字符串会参与路径构造、文件名或命令参数拼接时，才需要显式拒绝纯空白与首尾空白；
      纯展示用途的字符串不必加，避免无谓的输入限制
    - 校验形式用命令式 if 加 throw 强类型异常（项目内 11 比 0 的既有惯例），
      不用 ValidateScript（错误消息泄露脚本源码）
    - 不做静默 Trim：静默改写会让返回值与实际落盘名不一致，制造另一种静默错误
  - 冲突提示：该文档第 44-46 行当前描述的是与新规则冲突的另一套方案
    （在 catch 块中捕获 Error 级中断后重新抛出类型化异常），
    追加本通则时须一并处理该冲突，否则文档内会出现两套互斥要求
  - 复核条件：若最终改用声明式校验（需先解决消息泄露源码问题并与项目惯例对齐），
    本通则中「命令式」这一条要求随之调整

[ ] 拆分 Invoke-ParallelUpscale：并行块内纯逻辑与副作用解耦，使成功路径可测
